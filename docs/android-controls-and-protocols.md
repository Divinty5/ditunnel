# Протоколы и управление Android VPN

## Движки

VMess AEAD использует общий импорт и конвертер Xray, как Windows. Поддержаны TCP, WebSocket, HTTPUpgrade и gRPC; `aid` должен быть равен нулю. Проверка TLS-сертификата остаётся обязательной. Профили доступны из подписок, `vmess://`, буфера обмена и QR-кодов.

AmneziaWG использует `libditunnel-awg.so`, собранный из общего с Windows SOCKS-моста в `runtime/amneziawg`. Ядро, Go и зависимости закреплены в `eng/amneziawg-runtime.json`, `go.mod` и `go.sum`; Android NDK закреплён в `eng/android-runtime.json`. Единственный системный TUN создаётся собственным `DiTunnelVpnService`, а AWG использует сетевой стек в памяти. Отдельное приложение AmneziaVPN не требуется. Поддержаны параметры AWG 1/1.5/2/3/3.1 из общего конвертера, IPv4/IPv6 endpoint и внутренние адреса, DNS, MTU и AllowedIPs. Транспортный UDP-сокет защищается через `VpnService.Protect` и привязывается к физической сети до первой отправки.

Системный TUN объявляет IPv4/IPv6 только при наличии внутреннего адреса и AllowedIPs соответствующего семейства в профиле AWG. DNS-серверы недоступного семейства исключаются из системной конфигурации, чтобы они не включали его повторно. Android блокирует не объявленное семейство по умолчанию; `allowFamily` не вызывается, выхода через физическую сеть нет. Это исправляет несоответствие TUN возможностям AWG. Устранение `ERR_CONNECTION_CLOSED` на ChatGPT подтверждено пользователем и сравнением журналов браузера после обновления Android до 0.5.9. Локальные тесты покрывают большое TLS 1.3 рукопожатие с X25519MLKEM768, двустороннюю передачу более 200 КБ через AWG и Xray, а также UDP размером 1200/1350/3000 байт по IPv4/IPv6.

Проверки 02–03.10.2026: отключение QUIC в Vivaldi не устранило `ERR_CONNECTION_CLOSED` на chatgpt.com. Пользователь позднее подтвердил, что проверял Android 0.5.8, поэтому эти результаты не относятся к исправлению семейства IP в 0.5.9. Другие сайты и приложение ChatGPT работают; тот же профиль в AmneziaVPN открывает сайт. На Windows программный клиент через AWG получил ответы ChatGPT по HTTP/1.1 и HTTP/2 с обоими вариантами DNS (внутри AWG и физической сети). Ответ HTTP 403 содержал `cf-mitigated: challenge`; Edge в отдельном тестовом профиле через Xray → AWG также получил страницу проверки Cloudflare без ошибки соединения. Vivaldi в headless-режиме не завершил проверку за отведённое время, его результат не интерпретировался как сетевой сбой. Эти проверки не воспроизводят системный TUN Android. Пользователь также подтвердил успешное открытие сайта в обычном Vivaldi на Windows через AWG. Ключ AWG передавался локальному процессу через канал с доступом только для текущего пользователя и не записывался в диагностические журналы. Проверка не изменяла системные маршруты.

Подключение AWG подтверждается свежим handshake с сервером. Служебный UDP-пакет внутри маршрутов Peer инициирует handshake; ответ на этот пакет не считается подтверждением доступности. При отсутствии handshake через 18 секунд туннель закрывается и отображается ошибка.

Трафик идёт по цепочке `Android TUN → Xray / правила → SOCKS5 на loopback → AWG netstack`. Для каждой сессии генерируются случайные логин и пароль SOCKS5. Поэтому работают блокировка рекламы, строгая блокировка и доменные правила Xray; выбранные для обхода соединения идут напрямую через защищённые сокеты Xray. Разделение по приложениям применяется на уровне Android VpnService.

Начиная с тестовой версии Android 0.5.8 (versionCode 50008), Xray работает в процессе `:vpn`, а AWG — в отдельном связанном процессе `:awg`. Это исключает загрузку двух независимых Go runtime в один процесс, которую документация libXray не поддерживает. Настройки передаются через Messenger IPC в неэкспортируемую службу того же приложения. При остановке сессии процесс AWG завершается вместе с его сокетами.

Проверка неподключённого AWG выполняется в отдельном процессе `:awgprobe` без системного TUN: быстрая дожидается handshake, точная выполняет HTTPS-запрос через SOCKS-мост. Измерение Handshake включает запуск ядра и ожидание рукопожатия, поэтому это не RTT. Общий предел проверки — 25 секунд для быстрой и 35 секунд для точной. Активный профиль проверяется HTTPS-запросом через сеть VPN. Только отсутствие ранее выданного системного разрешения VPN откладывает проверку с явным пояснением; отложенные результаты не удаляются фильтром недоступных серверов.

### NetLog Android 0.5.8: IPv6 при профиле IPv4

03.10.2026 разобран присланный пользователем журнал Vivaldi (Chromium 152, Android 16, стандартный режим записи). При начальном открытии chatgpt.com получен HTTP 200 через HTTP/2. После смены VPN браузер считает IPv6 доступным и соединяется с `[2606:4700:4408::ac40:9bd1]:443` через внутренний адрес TUN `fd00:19::1`. DNS содержит и IPv4, и IPv6 адреса, но локальный стек подтверждает IPv6 TCP за несколько миллисекунд: браузер перестаёт ожидать резервное IPv4-соединение. Затем отправляется ClientHello, принимается EOF без байтов ответа и возникает `SSL_HANDSHAKE_ERROR / ERR_CONNECTION_CLOSED (-100)`. Четыре повторных открытия главной страницы дают тот же результат. Все 30 ошибок TLS после смены сети связаны с IPv6; одновременно отдельное IPv4-соединение успешно согласует TLS 1.3. В проблемных попытках список ECH пуст; HTTP-ответа и проверки сертификата ещё нет.

Это подтверждает сбой пути IPv6 в проверенной 0.5.8 и соответствует несовпадению объявленных возможностей TUN и IPv4-профиля AWG. Исправление 0.5.9 ограничивает адреса, маршруты и DNS поддерживаемыми семействами. Результат исправления подтверждён на телефоне в 0.5.9; подробности повторной проверки приведены ниже. NetLog браузера не показывает внутреннюю ошибку AWG и не позволяет проверить отправку письма из отдельного почтового приложения; связь почтового сбоя с IPv6 остаётся предположением. Исходный журнал сохранён только в игнорируемом локальном каталоге диагностики.


### Подтверждение исправления в Android 0.5.9

03.10.2026 пользователь обновил приложение с 0.5.8 до 0.5.9 и подтвердил успешное открытие chatgpt.com в Vivaldi через тот же профиль AWG 2.0. Отправка письма, ранее не проходившая через AWG, также завершилась успешно.

Новый NetLog содержит 97 639 событий за 70,736 секунды. Оба открытия главной страницы chatgpt.com получили HTTP 200 через HTTP/2 и завершились без ошибки. Все девять новых TCP-соединений используют IPv4 через адрес TUN `172.19.0.1`; девять TLS-соединений успешно согласовали TLS 1.3. Проверка доступности IPv6 во всех 406 записанных событиях возвращает false. В журнале отсутствуют `SSL_HANDSHAKE_ERROR` и `ERR_CONNECTION_CLOSED`. Для сравнения, в журнале 0.5.8 проверка IPv6 возвращала true, а все 30 ошибок TLS после смены VPN происходили на IPv6-соединениях с EOF без ответа.

Таким образом, исправление объявления семейств адресов в 0.5.9 проверено на конкретном устройстве и профиле. Успешная отправка письма подтверждена пользователем; внутренний сетевой обмен отдельного почтового приложения NetLog браузера не записывает. Оба исходных журнала и скрипт сравнения хранятся в игнорируемом локальном каталоге `.tools/android-build-local/diagnostics`, без добавления содержимого журналов в Git.


## Плитка и виджеты

Android 0.5.11 обрабатывает долгое нажатие плитки через QS_TILE_PREFERENCES, открывая основной экран без переключения VPN. Исправление восстановления сети описано в [сценарии 5 октября](controls-recovery-validation.md): физическую сеть ждёт foreground-контроллер, который явно останавливает и повторно запускает нативный процесс. Закрытие окна не означает включения Always-on; эту опцию включает пользователь в системных настройках VPN.

В настройках разделения по приложениям «Автовыбор» добавляет установленный Vivaldi в режим проксирования выбранных приложений, а Mobifitness — в режим обхода. Распознавание учитывает идентификатор пакета и название приложения; существующий ручной выбор сохраняется.

В редакторе быстрых настроек Android можно добавить плитку **Di-Tunnel**. Она включает выбранный сервер или отключает VPN. После первой установки необходимо импортировать профиль и подтвердить системное разрешение VPN; при необходимости плитка открывает приложение для этого шага. На заблокированном экране требуется разблокировка.

Доступны пять виджетов: 1×1 с кнопкой, 2×2 с кнопкой и состоянием, 4×3, 4×4 и 4×5 с состоянием и списком серверов выбранной подписки. Выбор сервера сохраняется; при работающем VPN выполняется переключение туннеля, при отключённом — только меняется выбор. Размеры ячеек зависят от лаунчера. Кнопка и список временно недоступны во время перехода состояния.

Действия используют тот же `AndroidVpnEngine`, что и интерфейс. Короткий foreground-сервис поддерживает процесс управления до завершения команды. PendingIntent списка содержит идентификатор профиля, а конфигурация читается из зашифрованного хранилища. Отдельный атомарный файл состояния содержит PID и идентификатор профиля без ключей; перед восстановлением состояния и завершением процесса проверяется имя собственного VPN-процесса.

## Языки

Русский, английский, испанский и упрощённый китайский доступны в настройках. Общий каталог используется интерфейсом, сканером QR-кодов, плиткой, виджетами и уведомлениями. Уведомление активного VPN обновляется после смены языка. Служба VPN читает сохранённый язык, поскольку работает в отдельном процессе. В Android `locale-config` и нативных ресурсах перечислены все четыре языка.

## Граница поддержки

AWG 2.0 и исправление IPv6 в 0.5.9 подтверждены пользователем и NetLog. Полная проверка остальных вариантов, реального IPv6 и системного восстановления ещё не завершена: [результаты ревизии кода](amneziawg-support-review.md), [матрица устройств](android-release-validation.md).

В Android 0.5.10 включена поддержка системного Always-on VPN. Сервис использует Sticky и восстанавливает последнюю конфигурацию из хранилища, зашифрованного Android Keystore, без зависимости от открытого интерфейса. Перезапуск после потери служебного процесса и смены сети реализован; автозапуск после перезагрузки требует включённого системного Always-on. Блокировку трафика во время восстановления обеспечивает системная настройка «Блокировать соединения без VPN», а не Sticky. Возврат после потери сети подтверждён в Android 0.5.12; reboot, lockdown и расширенные сценарии без UI требуют проверки на телефоне: [порядок ручной проверки](awg-manual-validation.md). Явная остановка/отзыв разрешения отключают восстановление; при смене сети AWG пересоздаётся вместе с защищённым UDP-сокетом. Статус Reconnecting не считается подтверждением сетевой защиты.

## Локальная сборка и проверка

### Падение Mono на Android 16

Для присланного стека `libmonosgen-2.0.so` с BuildId `4efb763813573a1140dcdc5ea251cacf33529cbc` получены соответствующие символы Microsoft. Адрес `0x29d364` относится к `push_object + 16`, `0x29c090` — к `processing_stw_step`, а следующие кадры — к обработке GC-моста и сборке памяти SGen. Это путь Tarjan, для которого опубликован похожий [отчёт .NET runtime #123495](https://github.com/dotnet/runtime/issues/123495).

В `mono-environment.txt` задан `MONO_GC_PARAMS=bridge-implementation=new`: поддерживаемая альтернативная реализация GC-моста обходит Tarjan. Наличие `sgen_new_bridge_init` проверено в символах используемой версии Mono. Это мера совместимости, требующая длительной проверки на устройстве; причины повреждения памяти и отсутствие других нативных вылетов пока не доказаны. Настройка GC-моста описана в [документации Microsoft](https://learn.microsoft.com/ru-ru/xamarin/android/internals/garbage-collection).

Локальный workflow, SDK, NDK, keystore, пароли и результаты находятся в игнорируемой папке `.tools/android-build-local`. Они не добавляются в Git. Локальный `Build-AwgBridge.ps1` проверяет архив NDK и зависимости Go, собирает мост для ARM64/x86_64 и записывает SHA-256 библиотек; `Restore-AndBuild.ps1` вызывает его перед сборкой, а `Build-LocalApk.ps1` использует ранее созданный ключ. Для другого подготовленного окружения требуется `DITUNNEL_ANDROID_AWG_ROOT`, содержащий каталоги `arm64-v8a` и `x86_64`. Лицензии и происхождение библиотеки включаются в APK.

Перед выпуском на телефоне следует проверить:

1. Чистую установку, импорт AWG и VMess, подключение, внешний IP, DNS и несколько циклов включения/отключения.
2. Плитку с закрытым приложением, отказ и выдачу VPN-разрешения, состояние ошибки, экран блокировки.
3. Все пять размеров виджетов, выбор сервера своей подписки при включённом/выключенном VPN, удаление/обновление подписки, перезапуск приложения.
4. Все четыре языка на главном экране, в настройках, подписках, импорте, QR-сканере, плитке, виджетах и уведомлениях, включая смену языка при активном VPN.
5. Отсутствие ложного зелёного состояния при неверном AWG-профиле; сохранение AWG при фильтрации отложенных проверок; блокировку рекламы, обход доменов и разделение по приложениям.
6. Отмену подключения AWG и переподключения из меню подписок; после завершения отмены должен снова работать выбор другой подписки. Отмена проверки должна прерывать как ручной запуск, так и текущий проход Lowest.
7. Быструю и точную проверку AWG до подключения, явное сообщение при отсутствии VPN-разрешения и сохранение работающего VPN при проверке другого профиля. После успешного handshake подключение должно пройти этап Xray без прежнего таймаута.

Мост AWG сохраняет ABI 3: Android создаёт UDP-сокет в служебном процессе, вызывает `VpnService.Protect` и привязывает его к физической сети на управляемом потоке. Go получает дескриптор и дублирует его для своего транспорта. Исходный сокет принадлежит Android-обёртке до завершения ядра; обратного вызова в Mono из потока Go нет. Ошибки запуска ядра возвращают фиксированные коды без содержимого конфигурации. Без стека нового падения его причину нельзя считать установленной.

В меню подписок отмена проверки и подключения вынесена в фиксированную панель над списком. Отмена подключения остаётся видимой до завершения очистки при Connecting и Reconnecting, в том числе для операции, начатой плиткой или виджетом. Сначала отменяется текущий запрос движка, затем выполняется остановка; отмена не ждёт освобождения блокировки запуска. При отсутствии ответа STOP в течение пяти секунд завершается только собственный изолированный процесс `:vpn`, что закрывает его TUN и сокеты. Сообщение о неудачном запуске содержит этап и тип исключения. Последний фиксированный этап также сохраняется в приватном каталоге приложения для диагностики таймаута после нативного сбоя; адреса, профили и ключи там не записываются.

Сборка и автоматические тесты не заменяют эту проверку на устройстве. Публикация нового Android-релиза выполняется отдельно.
