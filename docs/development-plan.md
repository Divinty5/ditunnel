# Di-Tunnel — план разработки

Дата исходного плана: 5 сентября 2026 года. Обновлено 9 сентября 2026 года.
Статус: Windows-прототип 0.3.30 реализован и проверен в VM. Актуальные пользовательские возможности описаны в README.md, границы проверки — в docs/windows-tun-validation.md.

## Текущее состояние

Реализованы Windows TUN, DNS-маршрутизация, WFP kill switch для IPv4/IPv6, восстановление после смены сети, подписки, DPAPI-хранилище профилей, раздельное туннелирование доменов/IPv4 и адаптивный Avalonia UI. Следующие крупные этапы — выделенная Windows-служба, правила по приложениям, кодовая подпись и только затем рассмотрение других платформ.

## 1. Результат первого релиза

Windows-клиент для личного VPS: Connect → HY2-443 → системный трафик через TUN → Disconnect → восстановление сети. Критерий успеха — возможность ежедневно пользоваться Di-Tunnel вместо Hiddify, включая перезагрузку компьютера, сон и временную потерю сети.

Сохраняем C#, Avalonia, Xray-core и порядок платформ Windows → Android → Linux. Не реализуем собственные протоколы, криптографию или TCP/IP-стек. Облачный сервис, аккаунты, продажа подписок и управление VPS в этот план не входят.

## 2. Уточнения к исходной идее

- В текущей документации Xray есть Hysteria outbound версии 2 и встроенный TUN inbound. Основной кандидат — Xray с собственным TUN, а не заранее выбранный внешний tun2socks. Документация не доказывает совместимость конкретного бинарника с нашим сервером: это проверяется первым экспериментом.
- Wintun предоставляет виртуальный сетевой адаптер, но сам не переводит IP-пакеты в прокси-соединения. Обработку пакетов поручаем TUN-реализации ядра. Отдельный мост рассматриваем только при подтверждённом ограничении.
- HY2-443, HTTPU-8081, WS-8080, SS-8388 — названия профилей. В модели отдельно храним протокол, транспорт, TLS, адрес, порт и параметры аутентификации. Для HTTPU и WS нужно выяснить базовый протокол и серверные настройки; номера портов этого не определяют.
- Восстановление сети, минимальная обработка sleep/wake, смена интерфейса и политика IPv6 нужны уже в v0.1. Расширенные правила и полноценный kill switch остаются последующим этапом.
- Общими будут логика и значительная часть UI. Android потребует отдельного запуска приложения, адаптивной компоновки и собственного жизненного цикла VPN.

## 3. Архитектура и границы ответственности

```text
Avalonia UI / ViewModels
          |
Shared Core: профили, состояния, диагностика, настройки
          |
          +-- Xray adapter: конфигурация, запуск, логи, статистика
          +-- Platform adapter: сеть, права, секреты, lifecycle
                    |
Windows network host / Android VpnService / Linux network host
                    |
                 Xray-core
                    |
                   VPS
```

Предлагаемая структура, создаваемая постепенно:

```text
DiTunnel.sln
src/
  DiTunnel.App/                 Общие Avalonia Views и ViewModels
  DiTunnel.Desktop/             Точка входа Windows; позднее Linux
  DiTunnel.Core/                Модели, сценарии, интерфейсы
  DiTunnel.Infrastructure.Xray/ Генерация конфигурации и адаптер ядра
  DiTunnel.Platform.Windows/   Сетевые операции, права, хранилище секретов
  DiTunnel.Service.Windows/    Привилегированный сетевой host
  DiTunnel.Android/            Позднее: точка входа и VpnService
  DiTunnel.Platform.Linux/     Позднее: интеграция Linux
tests/
  DiTunnel.Core.Tests/
  DiTunnel.IntegrationTests/
docs/
  adr/                         Решения с причинами и ограничениями
assets/
  branding/
```

Core не зависит от UI, Win32, Android API и деталей запуска процессов. Начальные контракты: `IVpnEngine`, `INetworkController`, `IProfileStore`, `ISecretStore`, `IDiagnosticsService`. Не создаём универсальную систему плагинов и несколько реализаций ядра заранее.

Для Windows целевая схема — обычный UI и отдельная служба с необходимыми сетевыми правами. Служба управляет ядром и восстановлением сети; IPC доступен разрешённому локальному пользователю, команды ограничены VPN-операциями. Пути к исполняемым файлам фиксированы, UI не передаёт произвольные команды для запуска с повышенными правами. В эксперименте допустим отдельный консольный запуск с повышением прав.

У каждой сетевой настройки один владелец. Если Xray управляет адаптером и маршрутами автоматически, C# не дублирует эти действия: проверяет результат и выполняет согласованное восстановление. Разделение ответственности фиксируется после эксперимента.

## 4. Этапы и критерии завершения

### Этап 0. Проверить сетевую схему

1. Зафиксировать фактические параметры HY2: endpoint, SNI, проверка сертификата, способ аутентификации, obfuscation и параметры пропускной способности, если используются. Секреты хранить вне репозитория.
2. Выбрать конкретный стабильный релиз Xray, проверить происхождение артефактов и записать версию/контрольные суммы. Проверить доступность нужных HY2/TUN возможностей именно в нём.
3. Подключить HY2 через локальный loopback-прокси без изменения системных маршрутов. Отдельно проверить TCP и UDP: успешный HTTP-запрос не подтверждает UDP.
4. Проверить встроенный TUN на тестовой Windows: TCP, UDP, DNS, маршрут к самому VPS, отключение и аварийное завершение ядра.
5. Записать, какие настройки ядро восстанавливает само, а какие должен восстанавливать host. Проверить, нет ли захвата собственного исходящего трафика ядра.
6. Провести небольшой Android-эксперимент: способ встраивания ядра, передача TUN FD и исключение исходящих сокетов из VPN. Это проверка архитектурного риска, не разработка Android-релиза.

**Готово:** есть воспроизводимый сценарий Windows HY2 + TUN, обезличенный пример конфигурации и ADR о версии ядра/владении сетью. Если схема не работает, сначала локализуем ограничение и отдельно решаем вопрос о мосте или изменении ядра.

### Этап 1. Каркас приложения и репозитория

- Создать solution, общие проекты, Windows entry point и тестовый проект.
- Зафиксировать совместимые стабильные версии .NET SDK и Avalonia после проверки целевых ОС и Android workload; добавить `global.json` и централизованные версии пакетов.
- Поднять окно с состоянием подключения, кнопкой и заглушками показателей, используя тестовую реализацию VPN-интерфейса.
- Добавить README с запуском, `.gitignore`, CI сборки и тестов. Подготовить правила вклада и сообщения об уязвимостях; лицензию проекта выбрать отдельно с учётом распространяемых зависимостей.
- Подготовить фиктивные примеры конфигов. Публичную публикацию GitHub выполнять отдельным шагом после проверки содержимого и выбора лицензии.

**Готово:** чистая машина собирает приложение по README; UI переключает тестовые состояния без реального изменения сети.

### Этап 2. Управление ядром без TUN

- Типизированная модель одного профиля HY2, проверка обязательных полей и генерация конфигурации.
- Проверка конфигурации средствами закреплённой версии Xray до подключения.
- Запуск/остановка, ожидание готовности, таймауты, отмена, чтение stdout/stderr, обнаружение завершения процесса.
- Состояния: `Disconnected → Connecting → Connected → Disconnecting`; дополнительные `Reconnecting` и `Error`. Повторный Connect не создаёт второй процесс; Disconnect отменяет незавершённое подключение.
- Секреты отделены от настроек. Временные конфиги доступны только нужным процессам и удаляются; логи скрывают пароли, токены и ссылки с credentials.

**Готово:** через локальный прокси работает реальный запрос к сети; ошибки аутентификации и недоступность сервера отображаются понятно, отмена и падение процесса не оставляют зависшие подключения. Статус Connected требует проверки трафика, одного живого процесса недостаточно.

### Этап 3. Полноценное подключение Windows

- Реализовать привилегированный host, IPC и управление TUN по результатам этапа 0.
- До применения изменений записывать журнал принадлежащих Di-Tunnel настроек. При сбое выполнять обратные операции; при следующем запуске восстанавливать незавершённую сессию. Не перезаписывать чужие или обновлённые DHCP настройки устаревшим снимком.
- Настроить DNS через туннель и разрешение имени VPS до поднятия туннеля без циклической зависимости. Исключить из туннеля транспорт к VPS.
- Явно определить исключения: loopback, необходимые локальные сетевые протоколы; доступ к LAN — отдельная настройка, по умолчанию не обещать обход VPN для всей локальной сети.
- Для v0.1 либо туннелировать IPv6, либо блокировать его обход VPN на время соединения. При невозможности применить выбранную политику подключение завершается ошибкой; глобально отключать IPv6 в системе не нужно.
- Задать поведение без kill switch: при неисправности после попытки восстановления VPN возвращать обычную сеть и явно показывать отсутствие защиты. Не обещать блокировку трафика при падении ядра до реализации kill switch.
- Добавить reconnect с ограниченным backoff, обработкой смены сети и отменой пользователем; проверить sleep/wake.

**Готово:** Windows-трафик идёт через VPS, нет непредусмотренного DNS/IPv6 обхода в подключённом состоянии, Disconnect и аварии восстанавливают работоспособную сеть без ручных команд.

### Этап 4. Диагностика и ежедневный UX — v0.1

- Главный экран: профиль, состояние, Connect/Disconnect, IP выхода, RX/TX, длительность сессии, задержка и последняя ошибка.
- Экран логов: время, компонент, уровень, фильтр, копирование обезличенной ошибки.
- Разделить измерения: прямой probe до VPS, запрос через VPN и время установления соединения. Показывать метод и точку измерения. TCP connect/HTTP probe не подписывать как чистый сетевой RTT; timeout не трактовать автоматически как потери пакетов.
- Прямой probe привязать к физическому пути и проверить маршрут захватом пакетов. Если обход нельзя подтвердить, показывать «недоступно», а не сомнительную задержку. Не оставлять произвольные диагностические обходы для пользовательского трафика.
- Для RX/TX выбрать один источник и явно указать, считаются полезные данные или байты адаптера. Скорость считать по разности счётчиков и монотонному времени.
- IP выхода проверять запросом через VPN к заранее выбранному endpoint; сбой этого сервиса показывать отдельно от сбоя туннеля. Проверка IP создаёт внешний запрос — отразить это в настройках диагностики.
- Добавить базовый tray, понятное поведение закрытия окна, автозапуск приложения как настройку. Автоподключение — отдельный выключатель.
- Подготовить воспроизводимую Windows-сборку, установку/удаление службы, версии компонентов и инструкции восстановления.

**Готово:** пройдена матрица ниже и несколько дней личного использования без ручного исправления сети. Это критерий v0.1, а не просто наличие всех кнопок.

### Этап 5. Профили — v0.2

Добавить HTTPU, WS и Shadowsocks после фиксации реальных серверных параметров; несколько серверов, переключение, health-check и ручной выбор лучшего профиля. Затем импорт поддерживаемых ссылок, QR и подписок с ограничением размера, валидацией и безопасной обработкой некорректных данных. Импортированные данные не должны выбирать произвольные бинарники, команды или пути службы.

Автовыбор учитывает работоспособность и устойчивость, а не единственное минимальное значение задержки. Добавить задержку между переключениями и порог улучшения. Обновление подписки не уничтожает рабочие локальные профили при ошибке загрузки.

**Готово:** каждый заявленный профиль подтверждён на реальном сервере; переключение и импорт не оставляют неконсистентное состояние сети.

### Этап 6. Маршрутизация и защита — v0.3

Сначала доменные/IP-правила и DNS-политики с объяснением применённого правила; затем kill switch, полный dual-stack, журнал соединений и экспорт диагностики. Per-app routing оформить отдельным исследованием для каждой ОС: нельзя считать его автоматически доступным через общие routing rules Xray.

Обновления клиента и ядра вводить после стабилизации: проверка подлинности и целостности, совместимости конфигов, откат к рабочей версии, восстановление при прерывании установки. Не заменять работающее ядро посреди соединения.

**Готово:** правила подтверждены тестами маршрутов, kill switch проверен при падении ядра/службы и смене сети; диагностический экспорт не содержит секретов.

### Этап 7. Android, затем Linux

Android: общий Core/UI, отдельная мобильная компоновка, `VpnService`, foreground lifecycle, разрешение пользователя, передача TUN FD, защита исходящих сокетов, Wi-Fi ↔ мобильная сеть, отзыв VPN-разрешения и остановка системы. Выпустить сначала APK для личного тестирования. Не переносить Windows-модель запуска `xray.exe` механически.

Подробная рабочая архитектура, версии компонентов, границы общего/платформенного кода, этапы и критерии готовности зафиксированы в [плане поддержки Android](android-development-plan.md).

Linux: переиспользовать desktop UI и адаптер ядра; определить первую поддерживаемую среду, затем реализовать права/host, `/dev/net/tun`, интеграцию DNS с выбранным сетевым менеджером и упаковку. Не обещать сразу все дистрибутивы.

Android начинается после устойчивой Windows v0.1 и может предшествовать расширениям v0.2/v0.3. Полный набор desktop-функций не является обязательным условием мобильного MVP. Linux следует за рабочим Android MVP.

## 5. Проверка качества

| Уровень | Что проверяем |
| --- | --- |
| Unit | Валидация/генерация конфигураций; переходы состояний и отмена; backoff; скрытие секретов; миграции профилей |
| Интеграция | Реальный Xray, неверный конфиг, занятый порт, таймаут, аварийный выход; IPC и восстановление незавершённой операции |
| Сеть на тестовой Windows | TCP, UDP, DNS, IPv4/IPv6; прямой и туннельный пути; MTU и крупные передачи; недоступный VPS |
| Жизненный цикл | Повторные Connect/Disconnect, завершение UI/ядра/службы, перезапуск, сон, потеря сети, смена Wi-Fi/Ethernet |
| Установка | Чистая система, установка/удаление, отказ в повышении прав, восстановление после прерванной операции |
| Релиз | Секреты отсутствуют в конфигурациях примеров, логах и артефактах; версии зависимостей и уведомления об их лицензиях включены |

Сетевые проверки сначала выполнять в изолированной VM с возможностью восстановления, затем на рабочем компьютере. Тесты с VPS — отдельный запуск с локальными секретами, не обязательное условие публичного CI. Packet loss и реальные HY2 RTT показывать только при наличии проверенного способа измерения; иначе помечать показатель как неподдерживаемый.

## 6. Визуальное направление

Иконка задаёт основу: D-образный туннель, серебро, тёмная поверхность и фиолетовый акцент. В UI использовать спокойный фон и умеренное свечение вокруг основного действия; сохранить читаемость статусов и логов. Ошибки и состояние подключения обозначать не только цветом.

Исходный `icon.png` сохранить как мастер-концепт. Позже подготовить Windows ICO с проверкой на 16/24/32/48/256 px, упрощённую tray-иконку, Android adaptive icon и монохромный вариант. У исходника много мелких световых деталей и выходящий за D шлейф: при уменьшении нужны отдельная композиция и проверка на светлом/тёмном фоне. Финальные варианты не являются блокером сетевого прототипа.

## 7. Что понадобится перед реализацией

- Версия и архитектура Windows; позже — версия Android и модель тестового устройства.
- Параметры HY2 и сведения о серверном ядре. В репозиторий достаточно обезличенного примера; секреты используются только локально.
- Предпочтение по доступу к LAN, поведению закрытия окна и автоподключению. До уточнения: автозапуск/автоподключение выключены, закрытие в tray появляется только вместе с явным объяснением этого поведения.
- Выбор лицензии перед открытой публикацией.

Эти вопросы не мешают подготовить каркас. До проверки этапа 0 не фиксировать окончательный TUN-дизайн и сроки Android. Оценку сроков составить по фактическому результату эксперимента; критический путь — HY2 → TUN → восстановление сети → ежедневное использование.
