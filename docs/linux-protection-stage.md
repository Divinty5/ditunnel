# Linux: раздельное туннелирование и kill switch

Дата: 8 октября 2026 года. Этот этап расширяет [базовый Linux VPN](linux-vpn-stage.md). UI Avalonia и настройки общие; преобразование политики, привилегированные операции и управление nftables реализованы в Linux backend. Результаты испытаний и ограничения приведены в [отчёте VM](linux-vm-testing.md).

## Раздельное туннелирование

Поддержаны «Всё через VPN», «Обход выбранных» и «Только выбранные через VPN». Два последних режима имеют отдельные списки доменов/IP и приложений. Linux использует абсолютный путь фактического executable, с учётом регистра. UI читает `.desktop` и позволяет выбрать executable вручную. Выбранный домен, IP или процесс направляется в соответствующий outbound общего Xray builder; контрольный трафик использует противоположный путь.

Системный DNS остаётся общим. TCP/UDP порт 53 и настроенные адреса DNS имеют правило `proxy` перед пользовательскими правилами, в том числе в режиме ProxySelected и при разрешённой LAN. Доменные правила используют sniffing HTTP/TLS/QUIC; зашифрованный hostname, ECH, собственный DoH и протокол без определяемого имени требуют отдельной проверки или правила IP/приложения. Приоритет правил: VPN DNS, разрешённая LAN, блокировка рекламы, домены/IP, приложения, default outbound.

Транспорт VPN имеет SO_MARK 51820, прямой outbound — 51821. Правило `51820/0xfffffffe` направляет обе метки в `main`; немаркированный трафик идёт в отдельную таблицу TUN. Эти метки устанавливает привилегированный runtime, а не пользовательские приложения.

## Исправление Linux runtime

Закреплённый Xray 26.3.27 пропускал unconnected UDP sockets с адресом `0.0.0.0`/`::`, неверно форматировал IPv6 из `/proc/net/*6` и передавал IPv6 process source в parser без скобок. Добавлена ограниченная модификация закреплённых исходников: [runtime/xray-linux](../runtime/xray-linux/README.md). Windows/Android runtime не изменяются. Данные исходного процесса не изменяются при преобразовании адреса; точное совпадение сокета имеет приоритет над wildcard; неоднозначное владение не выбирается случайно.

`Prepare-LinuxRuntime.py` проверяет module sum и SHA-256 исходников, применяет модификацию, запускает регрессии и собирает Linux binary. Изменённые MPL-2.0 файлы включаются в runtime. `XRAY-SOURCE.json` связывает версию исправления с SHA-256 бинарника. Служба не объявляет поддержку РТ со старым runtime и отклоняет правила процессов до изменений сети, если metadata отсутствует или бинарник не соответствует ей.

Для поиска чужого процесса службе добавлены CAP_SYS_PTRACE и CAP_DAC_READ_SEARCH, вместе с ранее требовавшимся CAP_NET_ADMIN. GUI остаётся обычным пользователем; изменения сети разрешает polkit. Обоснование process matching: [Xray routing](https://xtls.github.io/en/config/routing.html); закреплённый исходник: [Linux finder](https://github.com/XTLS/Xray-core/blob/v26.3.27/common/net/find_process_linux.go).

## Kill switch

Служба создаёт собственную таблицу `inet dtks_<owner>`, с идентичностью владельца в comment. Пакет правил применяется атомарно до запуска runtime и перенаправления маршрутов. Цепи output и forward имеют policy drop. Разрешены loopback, TUN, узкий VPN transport и прямой runtime outbound. Для физических выходов недостаточно одной метки: одновременно проверяются UID 0 и cgroup v2 сетевой службы; транспорт также ограничен адресом, портом и протоколом сервера. Общего разрешения `established/related` нет.

При работающем VPN прямой трафик разрешённых правил РТ допускается. При потере runtime или владельца этот runtime останавливается, а firewall остаётся в ядре. Прямые приложения автоматически не получают исключения. DHCP и IPv6 neighbour discovery сохраняются как необходимые управляющие протоколы.

Опция LAN разрешает локальные/private сети IPv4/IPv6 и добавляет соответствующие direct routes внутри Xray. При отключённой опции LAN её исключения отсутствуют. Внешний DNS TCP/UDP 53 блокируется до LAN исключений; системный resolved может обращаться к локальному stub и DNS через TUN.

Политика использует [nftables socket cgroupv2](https://netfilter.org/projects/nftables/manpage.html). Чужие таблицы и rules не сбрасываются; удаляется только таблица с проверенной идентичностью Di-Tunnel. Policy routing и DNS сохраняют прежний точный ownership rollback.

## Жизненный цикл и IPC

Протокол D-Bus повышен до версии 2. `Connect` принимает ограниченный JSON настроек вместо команд или Xray/nft script. Проверяются режим, размеры, домены/IP и абсолютные пути. Capabilities сообщают KS и РТ отдельно; status передаёт фактическую защиту. UI и служба должны обновляться вместе.

Owner journal версии 2 содержит только owner, version и признак KS, с режимом `0600`. Маршруты, DNS и частные конфигурации очищаются независимо от firewall. После падения Xray/AWG, потери D-Bus клиента, SIGTERM или SIGKILL службы KS сохраняется. Новый host выполняет восстановление маршрутов с `releaseProtection=false`, сообщает Error/Protected и предлагает «Восстановить сеть».

Штатный Disconnect успешно подключённого владельца явно освобождает KS после очистки runtime. Автоматическая очистка неудачного Connect не снимает защиту. RestoreNetwork требует polkit; отказ сохраняет блокировку. Ошибка удаления собственных объектов сохраняет журнал для повторного восстановления. UI различает настроенную опцию и подтверждённое состояние защиты.

## Границы текущего этапа

- С включённым KS смена профиля или применение сетевых настроек требует явного отключения и нового подключения. Автоматический Disconnect/Connect запрещён, чтобы не открывать сеть между защищёнными сессиями. Бесшовный handoff и автоматический reconnect под сохранённым KS — следующий шаг.
- KS активируется при подключении. Политика до входа пользователя и сохранение после перезагрузки ОС ещё не реализованы: journal находится в `/run`, а правила — в памяти ядра.
- Snap/Flatpak, shell launchers, отдельные namespaces, общие SO_REUSEPORT sockets и моментальное завершение процесса не имеют универсального гарантированного process matching. В UI нужно выбирать реальный executable сетевого процесса; sandbox/дочерние процессы проверяются отдельно.
- Реальный AWG handshake, остальные варианты транспорта, публичный IPv6, suspend/uplink switch и совместимость со всеми UFW/Docker политиками ещё входят в релизную матрицу.
- `.deb` и desktop integration остаются отдельным этапом.
