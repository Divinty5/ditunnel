# Проверка Windows TUN, DNS и kill switch

Документ фиксирует проверенное поведение прежнего сетевого модуля Windows в изолированной Windows 11 VM. С 0.5.7 PowerShell-host заменён модулем C#: полный системный прогон новой реализации ещё требуется. Прежние результаты ниже не подтверждают работу нового модуля.

## Реализованная схема

- Xray-core создаёт TUN на базе Wintun.
- Независимый `Di-Tunnel.NetworkHost.exe` назначает адреса, маршруты и DNS-политику, следит за Xray и выполняет обратные операции. Маршруты и адреса настраиваются через IP Helper API, DNS — через системный CIM-провайдер без PowerShell.
- Интерфейс работает с обычными правами. Сетевой процесс запускается отдельно через UAC; именованный канал проверяет PID процессов на обоих концах. Ограниченный протокол передаёт только профили, сетевые настройки и операции подключения/проверки/отключения.
- Потеря интерфейса или канала отменяет запросы и вызывает очистку. Если завершён сам сетевой процесс, Windows Job Object завершает его дочерние ядра; при включённом kill switch постоянные правила WFP сохраняют блокировку до восстановления.
- Серверный IPv4-адрес получает точный маршрут через физический интерфейс, чтобы транспорт VPN не попал внутрь собственного туннеля.
- Kill switch создаёт транзакционно управляемые правила Windows Filtering Platform для IPv4 и IPv6: разрешения устанавливаются до завершающих блокировок.
- WFP-объекты имеют постоянные идентификаторы владельца Di-Tunnel. Очистка не затрагивает пользовательские правила брандмауэра и другие VPN.
- При потере сети WFP остаётся активным во время не более десяти попыток восстановления.

## Проверки нового модуля 0.5.7

- Собраны автономная версия `win-x64` и установщик 0.5.7, проверены SHA-256 и наличие клиента, сетевого модуля, Xray, Wintun и AmneziaWG в комплекте. GitHub-релиз не опубликован.
- Пройдены 41 тест платформы Windows: кадры IPC и PID участников, владение маршрутами при одновременной проверке сервера, порядок включения WFP, отмена запуска и очистка после частичного сбоя, отказ подключения при запрете сокета Windows или контрольном маршруте вне TUN. Изменение сети и DNS-политик в этих сценариях проверялось на тестовой реализации ОС.
- На текущей Windows 10 прочитаны таблица маршрутов и DNS через нативные API/CIM. Пользователь подтвердил подключение и работу Di-Tunnel отдельно; при совместной работе с AmneziaVPN получен запрет доступа, в её WFP-политике обнаружены блокировка интернета и разрешение только собственного адаптера.
- Пройдены 92 теста ядра, 45 тестов Xray-инфраструктуры и 54 теста приложения. Проверены переводы на четырёх языках, сохранение предупреждения TUN и выбор обновлений по платформе. Установка 0.5.7 и обновление через опубликованный GitHub-релиз ещё не проверены.
- Воспроизведён и исправлен PRECHECK на Windows 10 при отсутствии NRPT-правил: DNS-провайдер возвращает пустой ответ. Повторные проверки чтения локальных/действующих правил DNS и поиска физического интерфейса прошли на компьютере пользователя без изменения сетевых настроек. Добавлены проверки пустых ответов, сохранения существующих записей и явного отказа в доступе; ошибки PRECHECK теперь указывают операцию, а журнал содержит тип исключения и числовой код без данных профиля.
- Запуск через UAC, повторные подключения, восстановление при завершении процесса и отсутствие утечек нужно проверить отдельным системным прогоном. Отсутствие срабатываний корпоративного антивируса не подтверждено.

## Проверено вручную

На Windows 11 подтверждены:

- подключение Hysteria 2, VLESS TCP/WebSocket/HTTPUpgrade и Shadowsocks;
- полный системный TUN и штатное восстановление маршрутов/DNS;
- переключение профиля при активном VPN;
- раздельное туннелирование доменов, поддоменов и IPv4-адресов в обоих направлениях;
- работа выбранных прямых исключений без kill switch;
- блокировка прямого IPv4, IPv6 и DNS при активном kill switch;
- сохранение блокировки при отключении Ethernet;
- автоматические попытки восстановления без появления прямого IP;
- прекращение восстановления после десяти попыток с сохранением блокировки;
- IPv4- и IPv6-выход через VPN;
- Extended DNS leak test: только резолверы Cloudflare в стране VPN-сервера, DNS хоста не обнаружен;
- закрытие приложения установщиком без страницы Restart Manager и корректный запрос UAC.

## Автоматические проверки

При прежнем прогоне в VM набор содержал 102 теста: 37 Core, 30 App и 35 Infrastructure/Windows/Xray. Release-сборка Windows/Avalonia и WFP self-test в VM проверяли создание, перечисление и удаление собственных provider, sublayer и filters. Проверки нового модуля перечислены отдельно выше.

## Как повторить основную проверку

1. Для базового прогона убедиться, что другой VPN отключён. Переключение с Hiddify, Amnezia и WireGuard-подобных клиентов проверять отдельным прогоном: Di-Tunnel должен выбрать физический uplink, оставить чужой адаптер нетронутым и либо перехватить маршруты, либо сообщить о блокирующем kill switch другого клиента.
2. Подключить Di-Tunnel с включённым kill switch.
3. Проверить `curl.exe -4 https://api.ipify.org` и `curl.exe -6 --max-time 10 https://api64.ipify.org`.
4. Запустить Extended test на `https://www.dnsleaktest.com`.
5. В цикле проверять DNS и внешний IPv4, затем выполнить `Disable-NetAdapter` для физического интерфейса.
6. До восстановления VPN должны наблюдаться только блокировка или пустой результат, но не прямой адрес.
7. После `Enable-NetAdapter` дождаться автоматического восстановления либо десяти попыток и устойчивого защищённого состояния ошибки.

## Ограничения проверки

- Раздельное туннелирование приложений не реализовано.
- VMess и произвольный Xray JSON не являются рабочими подключениями.
- Работа зависит от корректности конкретного сервера, TLS/SNI и подписки.
- Полный цикл сна/пробуждения проверен менее подробно, чем отключение/возврат сетевого адаптера.
- UI и сетевые операции пока работают в одном повышенном пользовательском сеансе; выделенная служба остаётся будущим усилением границы привилегий.

## Диагностика

При совместной работе с AmneziaVPN её WFP-правила `Block Internet` и `Allow usage of VPN Adapter` могут разрешать трафик только через адаптер AmneziaVPN. Маршруты Di-Tunnel не отменяют этот запрет. Для совместной проверки нужно отключить KillSwitch и режим «Блокировать подключения без VPN» в настройках самой AmneziaVPN и переподключить её. Правила корпоративной защиты менять не требуется. Одновременный запуск двух клиентов не создаёт автоматически цепочку из двух VPN.

Явный запрет сокета Windows (10013) или контрольный маршрут вне TUN теперь отменяет подключение и запускает очистку, без события `CONNECTED`. Таймаут одного контрольного адреса остаётся предупреждением; успешная проверка профиля не заменяет его сообщением об исправности системного туннеля. В журнал записываются тип исключения и числовой код сокета без исходного текста исключения.

`%LOCALAPPDATA%\DiTunnel\last-network.log` содержит только разрешённые коды этапов и сетевых событий. Предыдущие журналы помещаются в подпапку `logs`. Ссылки подписок, адреса серверов, ключи, пароли и сырой stderr Xray туда не записываются.

Если штатная очистка не завершилась, используйте `scripts\Repair-DiTunnelNetwork.ps1` от администратора. Скрипт удаляет только собственное состояние Di-Tunnel и отказывается работать при активном сетевом host.
