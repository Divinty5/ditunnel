# Проверка Di-Tunnel в Ubuntu Desktop VM

## Установочный пакет Linux 0.6.0: 8 октября 2026 года

В той же изолированной Ubuntu 24.04 amd64 собран и установлен self-contained пакет `Di-Tunnel-0.6.0-linux-amd64.deb`. Windows и Android сохраняют версию 0.5.19. Прежняя ручная установка, включая SDK и переопределения systemd, сохранена отдельно внутри VM; её каталоги не подменяют файлы пакета. Проверки выполнялись только в гостевой ОС с синтетическим профилем и сервером.

На Ubuntu в Release прошли 356 managed tests: Core — 98, Infrastructure — 88, App — 107, Linux platform — 63. UI и host опубликованы с собственным .NET. Проверка архива подтвердила версию, SHA-256, amd64 ELF, владельца root, права каталогов/исполняемых файлов и синтаксис maintainer scripts. Desktop entry прошёл `desktop-file-validate`.

Для проверки upgrade использована фикстура 0.5.99: тот же пакет с изменённым только Debian control version, затем установлен окончательный 0.6.0. Это проверка upgrade lifecycle, а не совместимости с ранее выпущенным Linux-пакетом. Все пять сценариев пакетного lifecycle завершились PASS и exit 0. Скачанный на Windows окончательный архив проверен по SHA-256.

Доступные native зависимости проверены при установке и запуске. Необязательный .NET LTTng trace provider требует отдельной совместимой библиотеки для диагностической трассировки; она не нужна для проверенной работы GUI и службы. Полный сценарий загрузки обновления из GitHub ещё не проверен: релиз не опубликован; выбор asset и разбор именованной checksum покрыты автоматическими тестами. Проверка на физической Ubuntu в институте остаётся отдельным шагом. Остальные сетевые границы перечислены ниже и в [описании защиты](linux-protection-stage.md).

## РТ и kill switch: 8 октября 2026 года

Проверена окончательная сборка в той же Ubuntu Desktop VM, после checkpoint `before-split-killswitch`. Служба использует CAP_NET_ADMIN, CAP_SYS_PTRACE и CAP_DAC_READ_SEARCH; GUI остаётся обычным пользователем. Установлен Linux Xray, собранный непосредственно в Ubuntu командой `Prepare-LinuxRuntime.py --test`, с проверкой закрепления и metadata версии 2. Тесты `common/net`, `app/router` и AWG bridge прошли. На Windows прошли 59 Linux platform tests и 107 App tests; сборки host/UI завершились без предупреждений и ошибок.

Заключительный расширенный прогон завершился exit 0. Захваты и синтетические журналы оставлены только в локальных ignored tools и VM. После испытаний точные PID/namespace синтетического сервера проверены и остановлены, veth и его тестовые маршруты исчезли, KS/journal/TUN отсутствуют. Обычный HTTPS после очистки вернул 200. Таймер простоя GNOME возвращён к стандартному значению.

Это проверка перечисленных сценариев на изолированном стенде. Реальный AWG handshake, остальные транспорты, публичный IPv6, suspend/uplink switch, firewall reload и институтская Ubuntu ещё не подтверждены. Бесшовный reconnect под KS и защита после reboot не реализованы; подробности — в [архитектуре и ограничениях](linux-protection-stage.md).

## История: базовый VPN, 7 октября 2026 года

Следующие разделы сохраняют результаты предыдущего этапа; замечания о недоступности KS/РТ относятся к сборке того дня.


Дата: 7 октября 2026 года. Проверена текущая разработческая сборка 0.5.19 на Ubuntu 24.04.5 LTS amd64, GNOME 46.0, kernel 7.0.0-38-generic, .NET 10.0.10. Hyper-V: 2 vCPU, динамическая память со стартом 2 ГиБ и максимумом 4 ГиБ. Это подтверждение базового Linux VPN, а не полного паритета с Windows/Android.

## Окружение

Использована отдельная установленная VM с контрольными точками `clean-install` и `before-integration-tests`. Сетевые изменения, службы, политики и тестовые серверы устанавливались только в гостевой ОС. Windows и WSL не использовались для системных VPN испытаний.

Установлены шаблоны из `packaging/linux`: systemd unit, D-Bus policy и polkit actions. Сетевой хост работает как root с `CapabilityBoundingSet=CAP_NET_ADMIN`, ограничением устройств, read-only системными каталогами и отдельным `/run/ditunnel`. GUI работает как обычный пользователь в GNOME через XWayland. .NET runtime установлен в root-owned каталоге; использован локальный `DOTNET_ROOT` override службы. Это ручная тестовая установка, не проверка `.deb`.

На чистой Ubuntu отсутствовал `libsecret-tools`. До его установки приложение показало ошибку защищённого хранилища и отключило импорт. После установки Secret Service стал доступен. Эта зависимость уже указана в [инструкции первого этапа](linux-first-stage.md) и должна войти в будущий пакет. Avalonia использовала программный рендеринг: GLX backend отверг `llvmpipe`, но окно работало через fallback.

Все профили синтетические. Тестовый VLESS TCP сервер без TLS, HTTP/UDP endpoints и DNS responder размещены в дополнительном сетевом namespace внутри VM, соединённом отдельной veth-парой. Использованы тестовые адреса документации и домены `.test`. Реальные подписки, серверы и ключи не импортировались.

## Исправления по результатам GUI проверки

- В Linux-настройках убран устаревший текст о том, что VPN ещё не реализован. Указано, что недоступны kill switch и LAN exception; переводы обновлены.
- Кнопка подключения обновляет сообщение при начале/успешном завершении подключения и после отключения. Старый текст об активном туннеле или предыдущая ошибка больше не сохраняются после успешного действия. Сообщение сетевого engine имеет приоритет.
- Добавлен регрессионный тест последовательности подключения/отключения после устаревших сообщений. Все 107 App tests прошли. Пересобранный общий UI повторно запущен в Ubuntu VM.
- Повторный GUI-цикл подтвердил сообщения «Подключаем VPN…», «VPN подключён» и «VPN отключён.» на соответствующих стадиях.

## Что ещё не подтверждено

- AmneziaWG handshake и передача данных с настоящим сервером; варианты VLESS TLS/Reality, VMess, Trojan, Shadowsocks и Hysteria 2. Синтетический VLESS TCP не доказывает их паритет.
- Публичный IPv6 egress, DNS TCP, DoH и приоритет корпоративных DNS-зон. IPv6 TCP/UDP и A/AAAA проверены на локальном стенде.
- Смена uplink/DHCP, suspend/resume, обрыв сервера, длительная работа и другие VPN/firewall configurations. Проверен один явный конфликт policy rule.
- Kill switch, LAN bypass, split/domain/process rules, adblock, tray/autostart, установка/обновление/удаление `.deb`: соответствующие возможности ещё требуют реализации и отдельных испытаний.
- Ubuntu физического компьютера в институте; его версия пока сообщена как предположительно 24.04.

После аварии базовый VPN восстанавливает обычную сеть. Блокировка прямого выхода при аварии не заявляется до реализации kill switch.

Локальные VM helpers, контрольные суммы, тестовые архивы, захваты и подробные журналы находятся в игнорируемой `.tools/linux-vm-local`. Они привязаны к идентичности этой VM и не являются переносимым установщиком. План следующих этапов: [Linux development plan](linux-development-plan.md).

После испытаний синтетические peer processes остановлены. Служба оставлена в состоянии Disconnected; TUN, собственные policy routes и журнал отсутствуют. Обычный HTTPS-запрос вне VPN успешно выполнен.
