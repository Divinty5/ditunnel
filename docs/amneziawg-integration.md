# AmneziaWG на Windows

## Реализованный backend

Windows использует отдельный `ditunnel-awg.exe`: официальное Go-ядро AWG и gVisor netstack с TUN в памяти. Мост принимает SOCKS5 TCP и UDP только на `127.0.0.1`; для каждой сессии создаются случайные логин и пароль. Xray направляет outbound через этот мост и продолжает обслуживать Wintun, доменные правила, split tunneling и блокировку рекламы. AWG не создаёт второй системный адаптер, службу или собственные маршруты.

```text
приложение → Wintun → Xray / правила → локальный SOCKS5 → AWG netstack
                                                      ↓
                                 UDP с физического IPv4 → AWG-сервер
```

Официальное ядро закреплено на `b5928efb6ca19f0153958460c3d141f04abc5c2e`; module version и checksum, Go toolchain и SHA-256 записаны в `eng/amneziawg-runtime.json`. Зависимости закреплены в `runtime/amneziawg/go.mod` и `go.sum`. Сборочный скрипт проверяет их, формирует checksum собственного бинарника и копирует лицензии, включая Go runtime, в `Runtime/AmneziaWG`.

Источники: [Go-ядро AWG](https://github.com/amnezia-vpn/amneziawg-go/tree/b5928efb6ca19f0153958460c3d141f04abc5c2e), [UAPI](https://github.com/amnezia-vpn/amneziawg-go/blob/b5928efb6ca19f0153958460c3d141f04abc5c2e/device/uapi.go), [netstack](https://github.com/amnezia-vpn/amneziawg-go/blob/b5928efb6ca19f0153958460c3d141f04abc5c2e/tun/netstack/tun.go). Проверены 30 сентября 2026 года.

## Импорт и конфигурация

На Windows доступны **+ → Из файла**, буфер обмена и ручной ввод. Поддержан клиентский `.conf` с `[Interface]` и одним `[Peer]`, также в Base64 или из HTTPS-источника. Ссылки AmneziaVPN `vpn://` декодируются из Base64URL и Qt qCompress (4 байта длины + zlib); контейнеры `amnezia-awg`/`amnezia-awg2` с `awg.last_config` преобразуются в клиентский `.conf`. Сохраняются встроенный `config` либо клиентские ключи, endpoint, адреса, DNS и поля AWG 2 из JSON. Учётные данные управления сервером не переносятся в профиль. Распаковка ограничена 2 МБ, длина проверяется, дубликаты JSON-полей отклоняются.

API-подписки Amnezia и доступ к управлению сервером без готового `last_config`, ссылки `awg://`, несколько peers и plain WireGuard без параметров AWG не поддержаны. Для таких экспортов требуется готовая клиентская конфигурация. Формат проверен по [официальному импорту AmneziaVPN](https://github.com/amnezia-vpn/amnezia-client/blob/master/client/core/controllers/selfhosted/importController.cpp) и [сериализации AWG](https://github.com/amnezia-vpn/amnezia-client/blob/master/client/core/models/protocols/awgProtocolConfig.cpp).

В 0.5.1 исправлена обработка native `config` с `DNS = $PRIMARY_DNS, $SECONDARY_DNS`: только эти DNS-поля подставляются из `dns1`/`dns2` экспортного контейнера, при отсутствии значений применяются `1.1.1.1`/`1.0.0.1`. Ключи и шаблоны пакетов не изменяются. Реальная ссылка пользователя проверена локально в памяти: импорт прошёл, ключи и ссылка в репозитории не сохранялись.

Сохраняются исходный профиль и параметры `Jc/Jmin/Jmax`, `S1–S4`, числа/диапазоны `H1–H4`, `I1–I5`, `HeaderProtectionKey`, padding и тайминги. Дубликаты, неизвестные поля и командные хуки отклоняются. `AmneziaWgProfileConverter` переводит ключи из Base64 в hex UAPI, сохраняет cryptokey routes `AllowedIPs` и keepalive, переносит `Address`, DNS и MTU в netstack. DNS suffix из поля DNS не используется; при отсутствии IP-резолверов применяются `1.1.1.1`/`1.0.0.1`. Эти запросы проходят внутри AWG.

Перед подключением и переключением runtime запускается с `-validate` и транспортом-заглушкой. Это позволяет ядру проверить шаблоны и взаимосвязь параметров без реальных UDP-сокетов и изменения сети. Ошибка конфигурации обнаруживается до остановки действующего туннеля. Проверка не доказывает, что сервер имеет совпадающие параметры.

Конфигурации находятся в сессионном каталоге с ACL текущего пользователя и SYSTEM. Командная строка содержит только путь к файлу и PID владельца. Сырой stderr и UAPI не попадают в UI или диагностический экспорт; сообщения ядра подавлены. После завершения сессии файлы удаляются, постоянные профили остаются защищены существующим DPAPI-хранилищем.

## Lifecycle, маршруты и WFP

`WindowsVpnEngine` выбирает backend до сетевых действий. `Run-Tunnel.ps1` создаёт прежний точный маршрут к внешнему endpoint через физический интерфейс, привязывает UDP AWG к физическому IPv4 и индексу интерфейса (`IP_UNICAST_IF`) и запускает мост. Случайный SOCKS-порт передаётся через атомарный readiness-файл. Локальный Xray outbound сохраняет loopback и не получает физический `sendThrough`; прямые outbounds продолжают использовать физический адрес. Потеря физического адреса или шлюза вызывает восстановление соединения с новым transport socket.

WFP разрешает UDP к AWG endpoint, loopback и системный интерфейс DiTunnel. Маршруты, NRPT/DNS, split tunneling и kill switch обслуживает прежний общий host. Внутренние адреса AWG принадлежат netstack; системный Wintun сохраняет технические адреса DiTunnel.

IP-резолверы из профиля передаются в NRPT и Xray. Для них создаются точные маршруты через Wintun, включая private DNS и IPv6; правило DNS в Xray имеет приоритет над обходом выбранных доменов во всех режимах. Привязка зашифрованного UDP к физическому интерфейсу исключает конфликт с таким маршрутом, когда DNS и внешний endpoint имеют один IP.

Независимый PowerShell-host наблюдает за обоими ядрами. Сбой AWG передаётся как `ERROR_AWG_EXIT`, при работающем туннеле защита сохраняется на время автоматического восстановления. Переключение AWG ↔ Xray использует существующий переход WFP. При штатной остановке host завершает процессы и удаляет принадлежащие ему файлы/маршруты/DNS. Сам AWG runtime наблюдает за handle процесса host и завершается при потере владельца, включая аварийное завершение host. При проверке сервера владельцем выступает UI-процесс.

С 0.5.2 быстрая проверка устанавливает SOCKS TCP CONNECT к `1.1.1.1:443` через Xray и AWG. Она не зависит от DNS контрольного домена, порта 80 и политики HTTP HEAD; это проверка назначения внутри туннеля, а не TCP-соединение с внешним UDP endpoint. Точная проверка сохраняет HTTPS-запрос. При уже активном VPN используется существующий механизм временного обходного маршрута и разрешения WFP.

В 0.5.3 исправлено завершение замера: Xray отправляет [успешный SOCKS CONNECT](https://github.com/XTLS/Xray-core/blob/v26.3.27/proxy/socks/protocol.go#L189) до подключения outbound, поэтому один этот ответ давал ложные значения около 1 мс. Теперь после CONNECT выполняется TLS-рукопожатие с `1.1.1.1`, с обычной проверкой имени и доверия сертификату. Замер включает путь через AWG и ответ контрольного узла; в UI обозначен `TLS`. Это время установления TLS-соединения, не ICMP RTT. Тест с немедленным CONNECT и задержанным на 250 мс TLS-ответом проверяет регрессию; зависший TLS не считается успешной проверкой, недоверенный сертификат отклоняется.

Название протокола включает версию. Для ссылок сохраняется поддержанное `awg.protocol_version`; для ранее импортированных профилей версия выводится из параметров: базовые — 1.0, I-пакеты — 1.5, S3/S4 или H-диапазоны — 2.0, header protection/padding/timings — 3.0, RandomTrailers/DisableCookies — 3.1. Это определение по конфигурации, а не результат переговоров с сервером. Тип хранимого профиля остаётся `AmneziaWG`.

## Ограничения

В 0.5.5 временный Xray для проверок открывает только TCP SOCKS-вход: UDP на том же номере порта мог быть занят даже при свободном TCP, что воспроизведено тестом настоящего Xray на loopback. Разрешение WFP удерживается на весь срок проверки и последующей очистки; очередь не входит в сетевой таймаут. Проверка уже подключённого AWG-профиля DT использует его действующий защищённый SOCKS-мост и удерживает сессию от переключения на время запроса. Для других AWG-профилей по-прежнему запускается временное ядро.

Одновременная работа AVPN и DT по одной AWG-конфигурации не гарантируется: один ключ идентифицирует одного peer, а его endpoint обновляется по последнему аутентифицированному пакету (см. [WireGuard roaming](https://www.wireguard.com/)). Для двух одновременно работающих клиентов нужны отдельные клиентские ключи и конфигурации на сервере. Проверка отдельным ядром той же конфигурации при активном AVPN также может переключать endpoint; DT не читает конфигурацию стороннего клиента и не завершает его сессию.

В 0.5.4 название быстрого режима обобщено, а фактический метод TCP/HTTP/TLS остаётся в результате. На Windows маршрут внешнего endpoint для проверки выбирается через физический uplink и при активном стороннем виртуальном адаптере, включая AmneziaVPN. Проверки одного IP выполняются по очереди, чтобы одна не удаляла временный маршрут другой; разные IP проверяются параллельно. Существующий точный маршрут не присваивается проверке и не удаляется при её завершении. Отмена дожидается завершения короткой маршрутной операции перед очисткой. Автотесты используют синтетические интерфейсы и подменённые сетевые команды; системная проверка с двумя активными VPN в этом изменении не запускалась. Если kill switch стороннего VPN запрещает физический uplink, обходной маршрут сам по себе не снимает запрет: настройки защиты стороннего клиента не изменяются.

- Реализован Windows x64 backend. Android пока импортирует и хранит AWG; его libXray не запускает этот Windows-мост.
- Внешний endpoint требует IPv4. Внутренний IPv6 поддержан netstack, если профиль и сервер дают IPv6-адреса и маршруты; иначе IPv6-запросы через AWG не проходят и не переводятся в прямой outbound.
- `AllowedIPs` ограничивает назначения внутри AWG. Для полного доступа нужны соответствующие default prefixes; адрес контрольного запроса `1.1.1.1` также должен быть доступен. Собственный DNS сервер должен попадать в разрешённые prefixes.
- Требуется совпадение параметров с сервером. Пройденные тесты AWG 1/2/3 не доказывают совместимость с любой конфигурацией или будущими версиями протокола.
- Гарантии системного kill switch/DNS для AWG требуют отдельного прогона в VM. Результаты прежнего Xray-прогона не считаются сетевой валидацией AWG.

## Сборка и безопасные проверки

```powershell
./scripts/Build-AmneziaWG.ps1 -Test
dotnet test tests/DiTunnel.Core.Tests/DiTunnel.Core.Tests.csproj
dotnet test tests/DiTunnel.Infrastructure.Xray.Tests/DiTunnel.Infrastructure.Xray.Tests.csproj
dotnet test tests/DiTunnel.App.Tests/DiTunnel.App.Tests.csproj
dotnet build src/DiTunnel.Desktop/DiTunnel.Desktop.csproj -c Release
```

Go-тесты используют два настоящих AWG-ядра с UDP только на loopback и виртуальными сетями из документационных диапазонов. Проверяются handshake и SOCKS TCP/UDP для AWG 1/2/3 с внутренним IPv4/IPv6, обязательная аутентификация, отсутствие fallback, ошибки обфускации, привязка сокета к loopback-интерфейсу и режим проверки без транспортных сокетов. При наличии закреплённого Xray проверяется полная цепочка Xray → SOCKS → AWG для TCP и UDP. C#-тесты проверяют преобразование UAPI, физический endpoint и loopback outbound, split rules, DNS-маршруты и смену физической сети с подменёнными cmdlets, проверку конфигураций самим бинарником и завершение runtime при потере тестового владельца.

Тесты Windows host подменяют системные сетевые операции и используют уникальный тестовый mutex в копии скрипта. Производственный `Global\DiTunnel.NetworkHost.v1` не меняется. Поэтому запущенный Di-Tunnel 0.4.33 не блокирует эти проверки и не останавливается ими.

## Результаты проверок без VM

На 30 сентября 2026 года пройдены:

- 92 теста `DiTunnel.Core.Tests`, 69 тестов `DiTunnel.Infrastructure.Xray.Tests` и 36 тестов `DiTunnel.App.Tests`: всего 197, без ошибок и пропусков. Импорт `vpn://` проверен на синтетических официальных контейнерах AWG 1/2, встроенном `.conf`, DNS-шаблонах, строковом/объектном `last_config`, повреждённых и чрезмерно больших payload. Проверены отображение и сохранение версии протокола, SOCKS TCP CONNECT с фрагментированным ответом, отказом и отменой, ожидание удалённого TLS и проверка сертификата.
- Go-тесты и `go vet`: настоящие AWG 1/2/3, внутренний IPv4/IPv6, TCP/UDP и цепочка с Xray.
- DNS-резолвер, существующий только в виртуальном серверном TUN: имя `only-in-awg.invalid` разрешается через AWG, затем устанавливается SOCKS TCP-соединение.
- Недоступный AWG endpoint: контрольный сокет основной системы не получает подключения; прямой fallback отсутствует.
- Сборка Windows x64 0.5.0 и установщика; SHA-256 опубликованного локального runtime и установщика совпали.

Только loopback-сокеты и сетевые стеки в памяти используются в реальных транспортных проверках; системные операции host подменены. Работающий Di-Tunnel 0.4.33 не останавливался, маршруты, DNS, адаптеры, WFP и службы основной системы не изменялись. Эти результаты подтверждают ядро и мост, но не доказывают системное отсутствие утечек при реальном VPN-подключении.

## Оставшийся системный прогон перед выпуском

Виртуальной машины пока нет. Backend остаётся экспериментальным до отдельной сетевой проверки; чувствительные сценарии предпочтительно выполнять в VM. Проверка на основной системе потребует отдельного окна без действующего туннеля и контроля восстановления сети:

1. AWG-профиль с тестовым сервером: внешний IPv4/IPv6, DNS resolver и отсутствие прямого выхода.
2. Все три режима split tunneling, блокировка рекламы и разрешённая локальная сеть.
3. Смена AWG ↔ Xray с включённым kill switch.
4. Недоступность endpoint, отключение/возврат физического интерфейса, смена IP и сна/пробуждения.
5. Отмена запуска, закрытие UI и аварийное завершение AWG, Xray и host по отдельности.
6. Отсутствие оставшихся процессов, сессионных ключей, маршрутов, NRPT и WFP после штатного отключения; сохранение блокировки при аварии до восстановления.
