# 0002 — Windows kill switch на базе WFP

## Статус

Принято и реализовано. Проверено в Windows 11 VM 9 сентября 2026 года.

## Решение

Di-Tunnel использует Windows Filtering Platform (WFP). UI не объявляет kill switch активным, пока сетевой host не подтвердит установку всех фильтров.

Host использует постоянные идентификаторы provider и sublayer, принадлежащие Di-Tunnel, и детерминированные ключи фильтров. В одной WFP-транзакции сначала устанавливаются разрешения, затем завершающие блокировки IPv4 и IPv6. Разрешения включают loopback, заранее разрешённый адрес VPN-сервера через физический путь, DHCP и необходимый link-local bootstrap. RFC1918, IPv6 ULA/link-local и локальное обнаружение разрешаются только по отдельной настройке.

При штатном отключении удаляются только собственные фильтры, даже если откат маршрутов сообщил отдельную ошибку. При аварии и намеренно включённом kill switch постоянные фильтры сохраняют fail-closed защиту. Следующий UI проверяет блокирующие ключи WFP и показывает оставшуюся блокировку; повторное подключение заменяет собственный набор атомарно. Явное отключение настройки или «Восстановить доступ к сети» удаляет собственные WFP/DNS-объекты через повышенный broker. Невозможность прочитать WFP возвращается как неизвестное состояние, а не подтверждённое отсутствие фильтров.

Windows 0.5.10 поддерживает выбор процессов: только закреплённому исполняемому файлу Xray разрешён прямой outbound, необходимый для выбранных пользователем split-правил. Произвольные процессы не получают общего разрешения WFP. При обычном отключении удаляются и эти исключения. Прямой трафик явно исключённых приложений является намеренным обходом VPN. Системная проверка описана в [сценарии 5 октября](../controls-recovery-validation.md).

## Причины

Один приоритет маршрута не блокирует прямое соединение после отказа TUN. Обычные правила Windows Firewall недостаточны: широкая блокировка может перекрыть отдельное разрешение транспортного соединения к VPN-серверу. WFP даёт управляемый порядок фильтров, отдельный sublayer, поддержку IPv4/IPv6 и изоляцию от пользовательских правил.

## Проверка

В изолированной Windows VM для прежнего сетевого host подтверждены:

1. прохождение транспорта VPN и блокировка обычного прямого трафика;
2. блокировка IPv4, IPv6 и DNS при потере TUN/физического адаптера;
3. сохранение fail-closed состояния во время десяти попыток восстановления;
4. отсутствие прямого IP при возврате сети;
5. штатное удаление собственных фильтров и восстановление подключения;
6. очистка собственных устаревших объектов встроенным self-test и recovery-скриптом.

Подробности и оставшиеся границы проверки приведены в `docs/windows-tun-validation.md`.

С Windows 0.5.7 сетевые операции выполняет отдельный модуль C#. Тесты проверяют порядок установки/очистки WFP и ошибки на подменённом сетевом слое. Прежняя VM-матрица не подтверждает полный системный прогон нового host и AWG; актуальная граница проверки — в [Windows validation](../windows-tun-validation.md).
