# Диагностика значка панели задач Windows

Статус на 14 октября 2026 года: собственный компонент Di-Tunnel без Windhawk успешно проверен пользователем на закреплённом диагностическом окне с ExplorerPatcher и со штатной панелью Windows 11. Полный логотип меняется сразу по F1/F2/F3 без исчезновения кнопки. Это подтверждено для кода компонента, перенесённого в приложение. После разрешённой проверки штатной панели восстановлено исходное значение OldTaskbar=2 с перезапуском Проводника. Пользователь исключил вариант с индикатором поверх логотипа.

## Собственный компонент

Реализация находится в `src/DiTunnel.ShellIcon`, управляемый клиент — в `WindowsTaskbarIcon.cs` и `WindowsShellSymbols.cs`. DLL загружается через адресованный потоку панели `WH_CALLWNDPROC`; служба, автозапуск и Windhawk не используются. MinHook 1.3.4 статически включён с лицензиями BSD; исходник модуля Windhawk не включён.

Подмена действует только во время получения/отрисовки значка работающей группы с AppUserModelID Di-Tunnel. Оба источника значка группы — `GetShortcutIDList` и `GetIconResource` — временно исключаются из выбора, чтобы панель использовала HICON окна. Именно второй источник отсутствовал в неработавшем собственном прототипе. Чужие группы, незапущенный закреплённый ярлык, группировка и порядок кнопок сохраняются.

Для ExplorerPatcher используются экспорты модуля. Для штатной панели функции разрешаются в отдельном процессе приложения по точным публичным PDB Microsoft: Windows 11 — `taskbar.dll`/`GetIcon`, классическая Windows 10 — `explorer.exe`/`_DrawRegularButton`. Первая загрузка символов после обновления Windows требует доступа к `msdl.microsoft.com`; затем используются кэшированные RVA с проверкой SHA256 образа. PDB не выполняется. Внутрь Проводника передаётся фиксированная структура через `WM_COPYDATA`, а не указатели другого процесса. DLL сверяет тип модуля, timestamp, размер PE и принадлежность всех RVA исполняемым секциям. Если версия, символы или функции не подходят, механизм не включается; окно и VPN продолжают работать.

На текущей Windows 11 разрешение символов штатной панели заняло около 4,6 с, повторное чтение кэша — 27 мс. Путь Windows 10 предусмотрен, но на отдельной Windows 10 визуально не проверен. Совместимость с будущими обновлениями Windows и защитным ПО не гарантируется.

Клиент реагирует на `TaskbarButtonCreated` и периодически проверяет PID Проводника, чтобы повторно подключиться после его перезапуска. При закрытии окна снимает Windows hook и перехваты; при аварии клиента срабатывает таймер проверки владельца. После снятия перехватов DLL освобождает собственную ссылку через барьер UI-потока. При невозможности безопасно снять/выгрузить компонент он удерживает ссылку вместо выгрузки исполняемого кода. Старая реализация смены цвета через запись ярлыков удалена; предусмотрено только однократное восстановление собственных старых ярлыков из `Icons/taskbar*.ico`.

Изолированные нативные тесты прошли 100 циклов для двух путей отрисовки: собственная/чужая/незапущенная группа, отсутствие влияния вне отрисовки, потеря владельца, сохранение HRESULT, снятие перехватов, частичная ошибка установки и несовпадающие PE/RVA. Изменение числа дескрипторов — 0. Тестовая DLL и её экспорт self-test в установщик не включаются.

В диагностическое окно дополнительно скопированы `DiTunnel.App.dll` и `DiTunnel.ShellIcon.dll` непосредственно из каталога опубликованного Windows-клиента. SHA256 нативного файла совпал с включённым в установщик: `743bd8eb618df8250dd91e019ef76aa8c96c1b1d8fb4fd141c254f97c12aa8be`. Подключение прошло успешно. При обычном закрытии компонент полностью выгрузился из Проводника без его перезапуска. После принудительного завершения только проверенного диагностического процесса компонент также полностью выгрузился; PID Проводника остался прежним.

Публичные Windows API до этого были проверены отдельно и не дали нужного результата. После их неудачи пользователь разрешил собственную DLL. Windhawk перед автономной проверкой выключен, его модуль отсутствовал в процессах Проводника. Пользователь затем подтвердил, что установленная новая сборка меняет значок на рабочем компьютере, Касперский предупреждений не выдаёт. Исключения и настройки антивируса агент не менял; результат относится к проверенной пользователем конфигурации.

## Воспроизведение

Проверена установленная версия 0.6.4. Её DLL совпадает с опубликованной сборкой; файл динамического ICO соответствует текущему состоянию. Это исключает устаревший процесс и неправильный цвет файла как объяснение наблюдаемой ошибки.

Минимальный тест использует Avalonia 12.1.2, обычное окно и смену `Window.Icon` по F1/F2/F3. Он не задаёт AppUserModelID, не меняет ярлыки и не использует VPN. Пользователь подтвердил:

- До закрепления полный значок на панели меняет цвет сразу.
- После закрепления это же окно перестаёт менять полный значок на панели.

В отдельном тесте со стабильным AppUserModelID и ярлыками полный значок остаётся фиолетовым при красном нативном значке окна. Это соответствует симптому установленного приложения.

## Проверенные подходы

- `WM_SETICON` для большого и маленького значков правильно обновляет заголовок, но не решает проблему закреплённой группы.
- Удаление и добавление кнопки через `ITaskbarList.DeleteTab/AddTab` вызывает нежелательное исчезновение кнопки и не решает закрепление; подход исключён из 0.6.4.
- Стабильный ICO, изменение собственных ярлыков и уведомления `SHChangeNotify/SHUpdateImage` не дали требуемого результата. В диагностике также проверены ключи `IExtractIconW.GetIconLocation` вместо предположения об индексе ресурса 0.
- Отдельный `ITaskbarList3.SetOverlayIcon(hwnd, NULL, NULL)` после создания кнопки возвращает S_OK. Видимый полный значок при этом не обновляется. Настоящий overlay в тесте не устанавливался.
- Изменение `System.AppUserModel.RelaunchIconResource` на новый файл текущего цвета вместе с явным AppUserModelID окна и повторной перерисовкой тоже не обновило видимый значок; результат подтверждён пользователем.

При разрешённом временном переключении ExplorerPatcher на штатную панель Windows 11 обновление группы также не заработало. Исходное значение OldTaskbar=2 восстановлено с перезапуском Проводника. Это наблюдение не доказывает работоспособность на всех версиях штатной Windows или ExplorerPatcher.

## Подтверждённый обход через Windhawk

По согласованию с пользователем подготовлена переносная копия Windhawk 1.7.3 из официального автономного установщика с действительной подписью Michael Maltsev. Служба, системная установка и автозапуск не создавались. Режим ExplorerPatcher OldTaskbar=2 сохранён; Проводник при включении теста не перезапускался.

Без изменения исходника собран модуль `taskbar-grouping` 1.3.11 из [репозитория Windhawk](https://github.com/ramensoftware/windhawk-mods/blob/main/mods/taskbar-grouping.wh.cpp). SHA256 проверенного исходного файла: `414b618caec622e826d8910d36cada9c09b30a84aebf48162ff46c7c16db5c51`.

Настройки теста:

- Движок ограничен процессом `C:\Windows\explorer.exe`: Include содержит этот путь, Exclude содержит `*`.
- `groupingMode=inverse`, список excludedPrograms пуст: сохранена обычная группировка приложений.
- `pinnedItemsMode=replace`, `oldTaskbarOnWin11=1` для текущей панели ExplorerPatcher.
- `useWindowIcons=0`; исключение `windowIconsPrograms` сначала содержало только диагностический процесс `DiTunnel.Icon.Smoke.exe`.

Пользователь подтвердил, что F1/F2/F3 меняют полный логотип диагностического окна на панели сразу, без исчезновения кнопки, в том числе после закрепления. Затем область действия расширена на AppUserModelID `DiVintyInteractive.DiTunnel` и `Di-Tunnel.exe`: после открытия установленного Di-Tunnel пользователь подтвердил, что цвет полного значка совпадает с кнопкой VPN. Проверка установившегося цвета реального приложения не включает автоматическое переключение VPN и отдельно не доказывает все переходы реального подключения.

После той проверки тестовый процесс был исключён; Windhawk временно оставался запущенным только с исключениями для Di-Tunnel. Позже, перед проверкой собственной DLL, Windhawk полностью выключен. Служба и автозапуск не создавались.

Переносная копия и команды запуска/отключения находятся в игнорируемом `.tools/WindhawkLab`. `Start-Test.ps1` запускает существующую копию, `Stop-Test.ps1` запрашивает штатный выход с выгрузкой модуля, `Set-Target.ps1` переключает область действия Probe/App/Both. Это внешний обход на проверенной системе, а не исправление автономного установщика Di-Tunnel и не подтверждение совместимости со всеми сборками Windows. После перезагрузки переносной Windhawk нужно запускать вручную.

## Границы доказательств

Тесты цветов HICON/ICO, файлов ярлыков, HWND, видимости и фокуса не проверяют фактическое изображение группы панели задач. Их успешное прохождение не является подтверждением исправления этого дефекта. Новый установщик с заявленным исправлением требует отдельной визуальной проверки установленного приложения с закреплением и без него.

Проверки выполнены на синтетических состояниях; маршруты, DNS, VPN-адаптеры и WFP не изменялись. Диагностические прототипы находятся в игнорируемом каталоге `.tools/TaskbarLab`; они не входят в установщик.
